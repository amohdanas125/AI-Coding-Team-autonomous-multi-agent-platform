# AI Coding Team — Phase 4 Scaffold

Multi-agent system that turns a plain-English app request into a working
CRUD web app (Express + React + MongoDB) built by 5 specialized AI agents.
Final-year B.Tech project.

## Status: Phase 5 (Documentation Writer, Surgical Retry & Packaging) Complete

The LangGraph topology, state threading, and QA retry loop are built and
tested. All 5 agents (`project_manager`, `backend_developer`,
`frontend_developer`, `qa_engineer`, and `documentation_writer`) are **real agents** now.
The test suite contains **86 offline tests**, all passing without API keys.

- **Task A (QA Engineer Hardening)**: Added `npx` existence checks, resilient token extraction in `helpers.js` (`res.body.token`, `res.body.accessToken`, etc.), increased timeout for in-memory MongoDB downloads (60s), and preserved test file paths in Jest failure logs.
- **Task B (Documentation Writer)**: Built `agents/documentation_writer.py` adhering to `DOCS_OUTPUT_SCHEMA`. API reference and setup guides (ports 3000 & 5173, seeding, env vars) are generated deterministically in Python; Gemini generates prose with an offline fallback.
- **Task C (Packaging & Assembly)**: Created `orchestrator/assembly.py` which writes `output/<app_name>/{backend,frontend}`, adds QA devDependencies, scripts, and helpers to backend, and packages the app as a ready-to-run `.zip`. Hooked into FastAPI `POST /build`, `POST /build/async`, and `GET /download/{clean_name}`. Verified `needs_human_review` flagging on retry exhaustion.
- **Task D (Surgical Retry)**: When QA fails, `find_failing_entities()` maps test failures to their owning entity. `generate_backend()` regenerates only failing entities with error logs in their prompts, reusing non-failing entity code, contract, and skeleton files. Global failures (npm install, jest crash) safely fall back to full generation.
- **Task F (Per-Entity Syntax Validation)**: Added `node --check` syntax validation and retry for per-entity model and router files in `generate_entity_backend()`.

**QA Engineer is a genuinely different kind of agent.** PM, Backend, and
Frontend only ever generate code - a human (or the live test scripts)
runs it afterward. QA Engineer generates Jest/Supertest test file content
via Gemini (one call per entity, same per-entity splitting pattern as
Backend Developer) and then ACTUALLY EXECUTES it: writes the backend's
files plus the tests into a sandboxed temp directory, runs `npm install`,
boots a real in-memory MongoDB (`mongodb-memory-server`) seeded with
Backend Developer's own already-generated `seed_records` (reusing
`seed.js`'s dependency-ordered fixtures rather than inventing separate
test data), runs Jest, and parses its real JSON output into
`QA_REPORT_SCHEMA`'s shape. **Not live-verified in the sandbox that built
this at all** - unlike every other agent, this one's execution step needs
network access to `mongodb-memory-server`'s MongoDB-binary download host,
which that sandbox never had. Run `scripts/test_qa_agent.py` yourself.

**Prerequisite change to Backend Developer: `server.js` split into
`app.js` + `server.js`.** Testing an Express app with Supertest means
importing the `app` object directly, without opening a real network
port - but `server.js` previously only ever called `app.listen()`, never
exporting anything. Now `app.js` creates and exports the Express app with
no DB connection and no `.listen()` call, and `server.js` is a thin
wrapper that loads env vars, connects Mongoose, requires `./app`, and
listens. `seed.js`'s insertion logic was similarly split: `seedDatabase()`
is now an exported function with no connect/disconnect of its own, callable
directly by QA's test setup (which is already connected to its own
in-memory MongoDB) without duplicating connection-lifecycle code, while
`node seed.js` from the command line still works exactly as before via a
`require.main === module` guard.

**A real bug found and fixed while building QA Engineer, before it ever
ran once:** `middleware/auth.js` (generated by Backend Developer, only
present when `auth_required` is true) reads `process.env.JWT_SECRET` and
throws at require-time if it's missing. QA's sandbox never writes a real
`.env` file, since it doesn't need `MONGODB_URI` there at all (the test
helpers connect directly to the in-memory instance's own URI) - which
means every auth-required app's QA run would have crashed on import,
before a single test even executed, for a reason with nothing to do with
whether the actual code works. Fixed by passing `JWT_SECRET` directly to
the Jest subprocess's environment. Caught by tracing the full execution
path by hand, not by seeing it fail live - this sandbox had no way to run
the code that would have hit it.

**Skeleton syntax validation, found live.** Backend Developer's skeleton
call returned `server.js` minified onto one line with one wrong bracket -
schema-valid, so nothing caught it until the live script's own
`node --check` pass. `generate_backend_skeleton()` now runs `node --check`
on every JS file it generates (alongside the existing `package.json`
JSON check), retries up to three times, and the prompt now forbids
minified one-line code. If `node` isn't on PATH the check is skipped
rather than blocking generation. The real broken line from that run is a
test case. Model and route files from the per-entity calls don't get this
check yet.

**Known limitation, deliberate not accidental:** on a QA-triggered retry,
`backend_developer` still sends the *entire* spec back to `generate_backend()`
for a full regeneration, not a surgical "fix only the failing entity"
pass - even though Jest's JSON output identifies exactly which test file
(and therefore which entity) failed, which is precisely what would make
that possible. Wiring that up is a real, valuable next step, deliberately
scoped out of this pass rather than bundled in with getting execution
working at all in the first place.

**Provider split: PM + Backend on Groq, Frontend on Gemini.** Not a full
migration — Frontend Developer's per-page calls were still occasionally
tight against Groq's 8000-token TPM ceiling even after splitting (a
many-endpoint app's `api_contract` alone could be sizeable), so only that
one agent moved. `gemini_client.py` mirrors `groq_client.py`'s
`call_agent(...)` interface exactly, so this was a one-line import change
in `agents/frontend_developer.py` and nothing else. `bedrock_client.py`
from an earlier attempt is still in the repo, untouched and passing its
own tests, but no agent currently imports from it.

**Automatic data seeding, added to Backend Developer.** Each entity's
Groq call now also returns 2 realistic `seed_records` for that entity's
own non-reference fields, piggybacked onto the existing per-entity call
(no extra API cost). `generate_backend()` assembles every entity's
records into a deterministic, plain-Python-generated `seed.js` — NOT
LLM-written — that inserts in dependency order and resolves reference
fields to the real `_id` of an already-inserted record. The model only
ever supplies field values, never insertion logic, for the same reason
`validate_payload()` never trusts a provider's schema claim blindly:
don't ask an LLM to get right what a program can guarantee instead.

**package.json content-validation fix, found live.** `npm start` and
`node --check` failed on *every single generated file* with the same
`ERR_INVALID_PACKAGE_CONFIG` — not 14 separate bugs, one: Node must read
`package.json` before checking any other file in the directory, so a
`package.json` whose content isn't valid JSON makes everything else in
the same folder look broken too, even files that are perfectly fine.
Root cause: the overall API response can pass full schema validation
(package.json's content is *a string*, and it was one) while that string
itself fails to parse as JSON — schemas.py had no way to check inside a
string field. `generate_backend_skeleton()` now parses package.json's
own content immediately after generation and retries (up to twice) if it
isn't valid JSON, raising a clear error naming exactly what's wrong if it
still isn't after retrying. `scripts/test_backend_agent.py` also no
longer prints 14 identical misleading stack traces for this case — it
collapses them into one diagnostic explaining what's actually going on.

**Cross-call naming consistency fix, found live.** `npm start` crashed with
`Cannot find module './routes/order'` — `server.js` (from the skeleton
call) and the Order entity's own router file (from a completely separate
call) had each independently derived "the lowercased entity name" and
landed on different strings. Same failure class as the seed-data
dependency-ordering problem: two LLM calls asked to independently derive
the same deterministic string can't be trusted to agree. Fixed the same
way — `_route_filename()` computes it once in Python, and both
`generate_entity_backend` and `generate_backend_skeleton` are explicitly
told the exact string to use, with `_enforce_route_filename()` as a
defensive rename if a call ignores the instruction anyway (tested
directly: a simulated model response naming its file `orders.js` instead
of `order.js` gets silently corrected before it ever reaches disk).

**Reference-field fix, found live.** A generated "Create Order" form sent
`{"restaurant": "Saffron Bistro"}` — the restaurant's *name*, typed as
free text — where the backend needed a real Restaurant `_id`, since
`Order.restaurant` is a reference field. Root cause: `api_contract`'s
`request_body_fields` was a bare list of field-name strings with no type
information, so Frontend Developer had no way to know *any* reference
field (on any page, in any generation) needed a real record picked
rather than typed. Fixed at the schema level: `request_body_fields` now
carries `{name, is_reference, references_entity}` per field
(`schemas.py`), Backend Developer emits it (`agents/backend_developer.py`),
and Frontend Developer resolves each reference field to the entity's
actual list endpoint via `_reference_field_lookups` — deliberately
searched against the *full* `api_contract`, not the page's already-scoped
one, since the referenced entity's own endpoint is very likely exactly
what per-page scoping filtered out.

**Design point worth remembering:** Frontend Developer is given the
Backend's `api_contract` — never its source code. `test_frontend_developer.py`
asserts this explicitly (a marker string planted in fake backend source
must never appear in Frontend's prompt), and separately confirms each
page's call only receives the `api_contract` entries relevant to its own
`primary_entity` (see `_relevant_endpoints`, the actual fix for Frontend's
rate-limit problem — filtering the contract down per page, not just
splitting the call).

**Rate-limit handling, per provider.** Groq's free tier is a hard
tokens-per-minute ceiling (8000, hit directly by both agents' original
single-call designs — 10760 and 11301 tokens requested) that no retry can
fix if a single request alone exceeds it; the real fix was splitting into
smaller calls (per-entity for Backend, per-page for Frontend) and scoping
each one's input down too. Gemini's free tier is gated on requests/minute
with a larger per-request budget, so a rate-limit hit there is more often
genuinely transient — `gemini_client.py`'s retry-with-backoff is more
likely to actually resolve it than Groq's. Both clients also retry
`groq_client.py`-specific malformed-JSON responses (`json_validate_failed`)
with a short 3s backoff, separate from rate-limit backoff, since that
failure is usually one-off sampling noise, not a hard limit.

## Run it

1. `pip install -r requirements.txt`
2. `pytest tests/ -v` — 70 tests, all offline. No credentials needed for this step.
3. `cp .env.example .env` and fill in `GROQ_API_KEY` and `GEMINI_API_KEY` (AWS fields only matter if you use `bedrock_client.py`).
4. `python scripts/smoke_test_groq.py` — confirms Groq strict mode works against the live API.
5. `python scripts/test_pm_agent.py` — runs the real PM agent against all 5 sample prompts.
6. `python scripts/test_backend_agent.py` — generates spec + backend + `seed.js`, writes files and `.generation-manifest.json` to `generated_apps/food-delivery-backend/`.
7. `python scripts/test_frontend_agent.py` — reuses that manifest, generates the React frontend into `generated_apps/food-delivery-frontend/` via Gemini, and **automatically runs `npm install && npm run build`** — the real JSX validation (`node --check` can't parse JSX at all, so it isn't used here). **Steps 4-7 could not be run in the sandbox that built this (no network access to api.groq.com or any Gemini/AWS endpoint there) — run them yourself.**
8. If step 7's build succeeds: `cd generated_apps/food-delivery-backend`, `npm install`, set up `.env` there (`MONGODB_URI`, `JWT_SECRET`), `npm start`, then in another terminal `node seed.js` to populate sample data; then `cd generated_apps/food-delivery-frontend && npm run dev`, open the printed URL, and actually click through it — register, log in, browse the seeded data, place an order.

## Design call made during scaffolding (not specified in the original brief)

On a QA-triggered retry, `backend_developer` routes straight back to
`qa_engineer`, **not** through `frontend_developer` again (see the comment
at the top of `orchestrator/graph.py`). Frontend didn't cause the backend
test failure and shouldn't be regenerated every retry — it only builds
once, on the first pass through the graph.
